## 1. Описание проекта и архитектурная концепция

Консольное приложение для службы кикшеринга «ВышКат». Система обеспечивает:
* Учёт прокатного транспорта (механические и электрические самокаты) с разделением по категориям сложности.
* Учёт сопутствующей инфраструктуры и вещей на балансе (защитные шлемы, зарядные станции, комплектующие/колёса).
* Автоматический расчёт суммарного суточного энергопотребления активного парка.
* Обязательный входной контроль техники через сервис техосмотра (`IServiceCenter`) перед постановкой на баланс.
* Внедрение зависимостей через легковесный типобезопасный `DIContainer`.

### Архитектурные слои:
1. **Domain Abstractions (`includes/ObjectPark.h`):** Чистые интерфейсы `IInventoryItem`, `IRentable`, `IEnergyConsumer`.
2. **Domain Entities (`includes/ObjectPark.h`, `src/ObjectPark.cpp`):** Иерархия моделей (`Wheel`, `Scooter`, `ScooterElectric`, `Helmet`, `ChargingStation`).
3. **Domain Services (`includes/ServiceCenter.h`, `src/ServiceCenter.cpp`):** Сервис техосмотра (`IServiceCenter`, `StandardServiceCenter`).
4. **Storage Layer (`includes/StorageCenter.h`, `src/StorageCenter.cpp`):** Хранилище объектов парка, полиморфный контроль уникальности инвентарных номеров.
5. **Infrastructure (`includes/DIContainer.h`, `includes/CreatorObject.h`):** Шаблонный IoC/DI-контейнер и расширяемая фабрика объектов.
6. **Application & UI (`includes/Park.h`, `includes/OwnerPark.h`, `src/main.cpp`):** Фасад парка и консольный пользовательский интерфейс.

## 2. Архитектура решения

### Интерфейсы (`includes/ObjectPark.h`)
* `IInventoryItem` — базовый контракт для вещей и техники на балансе (инвентарный номер, имя, метод `getSubItemIds()` для составных деталей).
* `IRentable` — прокатная техника со шкалой простоты `getSimplicity()` и предикатом `isForBeginners()`.
* `IEnergyConsumer` — потребители электроэнергии с методом `getDailyEnergyConsumption()`.

### Доменные сущности
* `Scooter` — механический самокат (`BaseRentable`, агрегирует колёса).
* `ScooterElectric` — электросамокат (`BaseRentable` + `IEnergyConsumer`, агрегирует колёса).
* `Wheel` — запчасть на балансе (`IInventoryItem`).
* `Helmet` — защитный шлем (`IInventoryItem`).
* `ChargingStation` — зарядный шкаф/станция (`IInventoryItem` + `IEnergyConsumer`).

### Сервисы и инфраструктура
* `IServiceCenter` / `StandardServiceCenter` — сервис входного техосмотра перед приёмкой.
* `StorageCenter` — хранилище объектов (категории `objectsEasy_`, `objectsNoEasy_`, `other_`), полиморфный контроль уникальности ID.
* `CreatorObject` — фабрика объектов на основе реестра `std::map<std::string, Creator>`.
* `DIContainer` — шаблонный контейнер внедрения зависимостей на базе `std::type_index`.
* `Park` / `OwnerPark` — фасад управления парком и консольный UI.

## 3. Обоснование принципов SOLID

* **S (Single Responsibility):** `ServiceCenter` отвечает только за допуск техники, `StorageCenter` — за хранение и поиск, `CreatorObject` — за парсинг ввода и конструирование, `OwnerPark` — за взаимодействие с пользователем.
* **O (Open-Closed):** Добавление новых типов объектов происходит через вызов `addCreator` в фабрике без правки её исходного кода. Проверка уникальности составных ID в хранилище работает универсально через `getSubItemIds()`.
* **L (Liskov Substitution):** Все сущности взаимозаменяемы в рамках базового контракта `IInventoryItem`. Прокатный транспорт корректно реализует контракт `IRentable`.
* **I (Interface Segregation):** Интерфейсы разделены по назначению. Например, `ChargingStation` реализует `IEnergyConsumer` и `IInventoryItem`, но не зависит от `IRentable`.
* **D (Dependency Inversion):** Класс `Park` зависит от абстракции `IServiceCenter`, а не от её реализации. Сервис внедряется через конструктор с помощью `DIContainer`.

## 4. Ответы на обязательные вопросы

### 4.1. Какой принцип SOLID применён наиболее явно и где?
* **OCP (Open-Closed Principle)** в `CreatorObject`: добавление новых сущностей осуществляется расширением реестра создателей без модификации существующего кода фабрики.
* **ISP (Interface Segregation Principle)** в `ObjectPark.h`: разделение контрактов `IInventoryItem`, `IRentable` и `IEnergyConsumer` позволило описать подвижной состав и стационарную инфраструктуру без лишних зависимостей.

### 4.2. Какой принцип сознательно ограничен / «почти нарушен» и почему это приемлемо?
* **DIP / SRP в `StorageCenter`:** Хранилище распределяет объекты по внутренним спискам (`objectsEasy_`, `objectsNoEasy_`, `other_`) при вызове `addObject`, а не делегирует это внешнему слою спецификаций (*Specification Pattern*).
  * *Причина компромисса:* Проект учебный. Создание отдельных микрорепозиториев и спецификаций для 5 классов привело бы к необоснованному усложнению (*overengineering*), за которое в критериях предусмотрен штраф.
* **Interface Querying в `Park::addObject`:** Применение `dynamic_cast<IEnergyConsumer*>` для выявления потребителей энергии. Это безопасный для C++ способ определения возможностей объекта (*capability query*), предотвращающий загрязнение базового интерфейса.

### 4.3. Что сломается (или не сломается) при расширении программы?
* **Новый вид транспорта (например, электровелосипед `ElectricBicycle`):** **Не сломается ничего.** Создаётся класс-наследник `BaseRentable` и `IEnergyConsumer`, регистрируется в фабрике и хранилище. Проверка уникальности составных ID работает автоматически через `getSubItemIds()`.
* **Сотрудник (`Employee`):** По ТЗ сотрудники **не ставятся на баланс**. Для них создаётся отдельный класс и сервис `StaffService`. Логика парка не сломается, так как сотрудник не является `IInventoryItem`.
* **Склад запчастей:** Уже поддержан архитектурно сущностью `Wheel` и категорией `other_`.

### 4.4. Какой тест фиксирует решение техосмотра и/или правило «для новичков»; как подменяется зависимость?
* **Файл с тестами:** `tests/test.cpp`
* **Подмена зависимости через DI:**
  В тестах вместо `StandardServiceCenter` в контейнер регистрируется мок/стаб:
  ```cpp
  DIContainer container;
  container.registerSingleton<IServiceCenter, AlwaysRejectServiceCenterMock>();
  OwnerPark owner(container);
  ```
  * **Фиксация техосмотра:**
  * Тест `TEST_CASE("ServiceCenter inspection via DI Container (Mock / Stub)")`:
    * Секция `"Mock completely rejects addition of vehicles"` проверяет, что при отказе мока объект бракуется, не попадает в парк, а счётчик энергии остаётся равным 0.
    * Секция `"Conditional mock rejects only defective vehicle by ID"` с классом `DefectiveIdServiceCenterMock` проверяет отклонение конкретного дефектного юнита при успешном приёме исправных.
  * Тест `TEST_CASE("Fix verification: Double Free and Transactional Energy")`: подтверждает, что при отказе в приёмке зарядной станции её киловатты не начисляются в баланс.
* **Фиксация правила «для новичков» (сложность >= 6):**
  * Тест `TEST_CASE("Behavior test: Beginner rules and energy calculation")`: проверяет распределение самокатов со сложностью 8 (>= 6, доступен новичкам) и 2 (< 6, для опытных), а также суммирование энергопотребления (25 + 40 = 65).

## 5. Сценарии работы в консоли (CLI)

### Команды меню:
* `1` — Справка по командам.
* `2` — Просмотр баланса парка (суммарная суточная энергия, техника для новичков, техника для опытных, вещи и запчасти на балансе).
* `3` — Приёмка нового объекта.
* `4` — Инструкция по форматам ввода и типам (`TypeObject`, `TypeWheel`).
* `5` — Выход из программы (корректное освобождение памяти по RAII).

### Примеры ввода:
```text
# 1. Добавление двух колес на баланс (SparePart = 4, ScooterWheel = 1):
wheel 10 4 1 12
wheel 11 4 1 12

# 2. Сборка электросамоката на созданных колесах:
# Формат: scooter_electric [id] [simplicity] [type=1] [kWh] [wheel1] [wheel2] [weight]
scooter_electric 1 8 1 25 10 11 15

# 3. Добавление шлема (Other = 5):
helmet 201 5 M

# 4. Добавление зарядной станции (OtherElectric = 3):
charging_station 301 3 120 8
```
